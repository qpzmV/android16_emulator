## 核心漏洞与风控埋点分析

### 1. 致命的逻辑自相矛盾（小米安全服务缺失）

```text
W ActivityManager: Unable to start service Intent { act=com.xiaomi.security.xsof.SAFETY_DETECT_SERVICE xflg=0x4 pkg=com.miui.securitycenter } U=0: not found

```

* **原理解析**：这是最致命的一个特征。小红书的 Native 引擎（`libtinyd.so` 或动态加载的加密 Dex）读取到你伪装的 `ro.product.model=2211133C` 后，断定这是一部小米设备。
* **风控策略**：既然是小米设备，它就会通过预埋代码去绑定（Bind）小米系统的核心安全服务 `miui.securitycenter` 的 `SAFETY_DETECT_SERVICE`（小米环境安全检测）。
* **穿帮原因**：你的 AOSP 镜像是通用的，根本没有小米特有的 `securitycenter.apk`。系统直接返回 `not found`。这种“属性是小米，但没有小米安全骨架”的矛盾，直接让小红书确信该设备是伪造的，NQE 分数瞬间被扣死。

### 2. HAL（硬件抽象层）名字泄露

```text
D android.hardware.audio@7.1-impl.ranchu: threadLoop: entering standby...
W android.hardware.audio@7.1-impl.ranchu: pcmWrite:259 pcm_writei failed...

```

* **原理解析**：你可能修改了属性，甚至修改了显卡驱动名称，但是音频硬件抽象层（Audio HAL）依然暴露了。`ranchu` 是 Android 官方模拟器的开发代号（QEMU/Goldfish 的后续升级版）。
* **风控策略**：风控引擎在后台会高频监控系统的硬件错误或日志输出，或者直接通过 `dlopen` 去枚举加载 `/vendor/lib64/hw/` 下的 `audio.primary.ranchu.so`。只要看到 `ranchu` 字符串，铁证如山。

### 3. 脱壳与动态 Dex 行为（反 Hook 核心）

```text
D nativeloader: Load ... /lib/arm64/libtinyd.so using isolated ns ...
W app_process64: hiddenapi: DexFile /data/user/0/com.xingin.xhs/app_cache/c4d121c215evx1s51d.dex is in boot class path but is not in a known location

```

* **原理解析**：小红书启动后，首先加载了 `libtinyd.so`（这是其核心加固与环境指纹收集的 C/C++ 库）。随后，它在内存中解密并动态释放加载了一个名字随机的 `c4d121c215evx1s51d.dex`。
* **风控策略**：这个动态 Dex 绕过了 Android 的常规安装校验，它被强行塞进了 `boot class path` 的虚拟上下文里（所以报了 `hiddenapi` 警告）。这说明核心的环境扫描算法（包括计算 NQE 分数的逻辑）全在这个动态加密的 Dex 里面，常规的应用层层面的 API 拦截对它完全无效。

### 4. 网络与时间同步异常

```text
W BestClock: java.time.DateTimeException: No network time available
E QTagParser: Error reading from /proc/net/xt_qtaguid/stats. Please check if this file exists.

```

* **原理解析**：App 尝试通过流量监控和基带时钟来核对当前的真实环境。
* **风控策略**：真实手机在亮屏激活时，基带（Telephony）和运营商网络通常已经同步了高度精确的 NTP 时间。而模拟器由于桥接网络或没有 SIM 卡，容易出现 `No network time`。同时，它读取 `/proc/net/xt_qtaguid/stats`（老版本 Android 用于流量统计的文件，现代内核可能被替换或切断），读取失败也成为了扣分项。

## 针对 AOSP 源码的下一步修改思路

既然知道了它是怎么看穿你的，你就需要利用 AOSP 的最高权限，针对性地进行“补天”：

### 思路 A：放弃伪装“大厂魔改系统”（推荐）

既然你伪装成小米会触发它去寻找 `miui.securitycenter`，那么最聪明的办法是**不要伪装成小米、华为、OPPO、VIVO 等有深度定制安全组件的品牌**。

* **做法**：在编译 AOSP 或修改属性时，将设备硬编码伪装成 **Google Pixel 官方原生系列**（如 Pixel 7 Pro / Pixel 8）。
* **优势**：Pixel 运行的就是原生 Android 系统，没有任何第三方大厂的特有安全 Service。小红书在识别到 Pixel 后，不会去寻找不存在的 `SAFETY_DETECT_SERVICE`，从而避开了这道必杀的逻辑陷阱。

### 思路 B：彻底清理 `ranchu` / `goldfish` 编译残留

风控能拿到 `android.hardware.audio@7.1-impl.ranchu`，说明你在编译 AOSP 镜像时，目标产品（PRODUCT）选取的依然是模拟器相关配置（如 `aosp_car_x86_64` 或 `sdk_phone_x86_64`）。

* **做法**：
1. 进到 AOSP 的 `hardware/` 和 `device/generic/goldfish/` 目录。
2. 找到所有编译生成 `*.ranchu.so` 或 `*.goldfish.so` 的 `Android.bp` / `Android.mk` 文件。
3. 全局将模块输出名称（`LOCAL_MODULE` 或 `name`）修改为常见真机芯片的硬件名称，例如 `audio.primary.default.so` 或 `audio.primary.msm8998.so`（高通）。



### 思路 C：动态伪造 Binder 服务响应

回到日志中被拦截的那些系统硬件服务，比如 `sensorservice`。

* **做法**：当第三方 App（`UID >= 10000`）去请求这些服务时，不要让系统直接在底层报 Permission denied 或返回 Null。
* **修改点**：在 `frameworks/base/core/java/android/app/SystemServiceRegistry.java` 或者底层的 `ServiceManager` 中，如果发现是小红书在 getService 某些敏感硬件，**返回一个全空实现的代理类（Proxy）**。这个代理类的方法被调用时全部返回 0 或正常值（比如加速度计永远返回微小的重力波动）。这样在小红书看来，硬件完好无损，只是手机被平放在桌子上动都没动。

### 思路 D：欺骗动态加载的 Dex（Bionic 层重定向）

由于小红书会动态释放诸如 `c4d121c215evx1s51d.dex` 这样的文件到其私有目录，并读取 `/proc` 下的信息。

* **做法**：在 `bionic/libc/bionic/open.cpp` 里面增加 UID 过滤代码：
```cpp
if (getuid() >= 10000) {
    if (strstr(pathname, "/proc/net/xt_qtaguid/stats")) {
        // 哪怕系统里没有这个文件，也重定向到一个你写好了伪造数据的静态文件
        pathname = "/system/etc/fake_xt_stats"; 
    }
}

```


这样它的动态加密 Dex 无论怎么读取底层文件，读到的都是你提前精心准备好的、充满真机特征的数据流。
