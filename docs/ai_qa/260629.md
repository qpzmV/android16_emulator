❯ 这个思路的原理是什么，为什么能成功

  Thought for 14s

原理

内核加载模块时，只检查一件事：.gnu.linkonce.this_module section 的大小是否等于内核的 sizeof(struct module)。

Google 内核 (6.6.66-android15):
  struct module = 1536 字节  ← 内核期望这个大小

我们编译的模块:
  struct module = 1280 字节  ← 用公开 goldfish-6.6 源码编译
  差 256 字节

这 256 字节差在哪里？ Google 内部有 8 个未公开的内核 patch 往 struct module 尾部加了若干字段。这些字段我们不关心（不影响模块功能），但内核的 sizeof() 检查不通过。

二进制补丁的做法：在 ELF 文件里把 this_module section 尾部的数据区扩大 256 字节（填零），同时更新 section header 里的 sh_size。内核一看 sh_size == 1536，通过。

补丁前: [---- 1280B 真实数据 ----]
补丁后: [---- 1280B 真实数据 ----][256B 零填充]
                                 ↑ 内核不读这部分，只检查大小

为什么 init 函数能正常执行？ struct module 的关键字段（init、exit、name、state）都在前面部分，Google 加的字段在尾部。填充零不影响前面字段的布局和值。

一句话：内核只检查结构体大小是否匹配，不检查那些多出来的字段有没有真实值。

❯ 又为什么能绕过app的环境检测呢

  Thought for 12s

因为 kprobe 挂在内核的 do_sys_openat2 上 — 这是所有文件打开操作的必经之路。

app 想探测 /vendor/bin/qemu-props:
  open()          ─┐
  __openat()      ─┤
  syscall(56)     ─┼──→ do_sys_openat2 ──→ 我们的 kprobe
  fopen()         ─┤         │
  FileInputStream ─┘    检测路径含 "qemu"?
                              │
                         是 → 返回 -ENOENT（文件不存在）
                         否 → 正常执行

为什么 app 绕不过去：

┌───────────────────────────────┬────────────────────────────┐
│        app 的绕过手段         │         我们的拦截         │
├───────────────────────────────┼────────────────────────────┤
│ syscall(__NR_openat) 直调内核 │ ✅ 在内核层，逃不掉        │
├───────────────────────────────┼────────────────────────────┤
│ shadowhook 劫持 libc open()   │ ✅ 我们挂在 libc 更底层    │
├───────────────────────────────┼────────────────────────────┤
│ Java File.exists()            │ ✅ 最终也是 openat syscall │
├───────────────────────────────┼────────────────────────────┤
│ native fopen()                │ ✅ 同上                    │
└───────────────────────────────┴────────────────────────────┘

和之前 bionic libc 拦截的区别：bionic 拦截在用户态，app 用 syscall() 就绕过了。kprobe 在 ring 0 内核态 — 没有更底层了。

Hunter SDK 的实际检测能力

Hunter SDK（libmodelprofile.so + libsentry.so）的检测手段我们已见过：
- 文件探测：stat /vendor/bin/qemu-props — 被我们拦截 ✅
- 属性查询：getprop ro.kernel.qemu — bionic 已拦截 ✅
- CPU 特征：model_score 上报 — 我们的 CPU 伪装在内核层，待验证

Hunter SDK 没有检测到以下行为：
- 没有扫描 /proc/modules（否则 NQE trace 会有对应的 open/read 记录）
- 没有检测 dmesg
- 没有检测 /sys/module/

一句话
